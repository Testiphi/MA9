# 车辆资料识别原型

目标是像 MAA 干员识别一样，把选车列表和车辆详情页转成有来源的结构化记录。`tools/probe_vehicle_fields.py` 处理**已有截图**；`tools/collect_vehicle_scan.py` 是独立的实机列表滑动/详情遍历采集器。它们均不点击比赛“开始”，也不改变多人循环的选车策略。

## 字段与判断边界

| 字段 | 来源 | 无法判断时 |
| --- | --- | --- |
| 车辆 ID、名称、级别（D/C/B/A/S/R）、所属段位 | OCR 名称匹配 `data/generated/vehicle_catalog.json`；要求最高匹配分与次高分有明显差距 | `null`，保留原始 OCR |
| 性能分当前值、上限 | 详情/列表的性能分 OCR | 未显示的上限为 `null` |
| 油量当前值、容量 | 燃油角标 OCR | 锁定或段位不可用、未显示油量时均为 `null`，不能当成 `0` |
| 星级当前值、星位总数 | 详情页星排的金色/灰色图像规则 | 图形不符合规则时为 `null` |
| 已有图纸、升星所需图纸 | 图纸角标 OCR | 只显示“最高”时，数值为 `null`，`blueprint_maxed=true` |
| 完全升级 | **选车列表**卡片底色：金色为 `true`，蓝色为 `false` | 详情页保持 `null`；不根据“最高”、满星或性能分相等推断 |

等级在数据中拆成 **车辆级别** 和 **性能分**，避免与星级混淆。OCR、颜色和图形判断各自保留原始证据；后续自动化只有在字段有值且可信时才能用它决策。

## 离线试用

在项目根目录运行 `tools/setup_dev.ps1 -SkipNode` 可建立虚拟环境。离线 OCR 目前仍需 MaaFramework 连接一个在线 ADB 控制器来初始化识别任务，但只读取指定截图，不操作游戏。首次使用可在被 Git 忽略的 `debug/vehicle_scan_env.json` 写入本机连接信息：

```json
{
  "adb_path": "你的 adb.exe 绝对路径",
  "address": "127.0.0.1:16384"
}
```

也可在命令行传入 `--adb`、`--address`，或设置 `MA9_ADB_PATH`、`MA9_ADB_ADDRESS` 环境变量。确认 MuMu 在线后运行：

```powershell
.venv\Scripts\python.exe tools/probe_vehicle_fields.py 'captures/多人游戏_车辆详情_Nissan Z GT4_可开始_TouchDrive开.png'
.venv\Scripts\python.exe tools/probe_vehicle_fields.py 'captures/多人游戏_选车_黄金_Nissan Z GT4完整可见_仅拥有开启.png' --screen list --annotate-dir debug/vehicle_scan_annotations
```

命令会将 JSON 输出到终端；加 `--output debug/vehicle_scan_result.json` 可直接保存 UTF-8 报告。选车列表现已自动定位所有完整可见卡片，`--card X Y W H` 仅保留为排查识别问题时的手动覆盖。自动定位在已有 48 张选车截图中都找到了至少一张完整卡片。

已用 Nissan Z GT4、Ferrari J50、Renault TREZOR、Nissan GT-R Nismo、Porsche Panamera Turbo S 等详情截图验证：满油、零油与不显示油量能分开；Z GT4 列表蓝卡、Ferrari 296 GTB 列表金卡能分开。当前星排位置与选车卡片底色的图像规则只针对现有 16:9 界面，尚需更多车型与分辨率的样本验证。

## 实机采集试跑

先在游戏里手动停在**多人选车列表**，再运行：

```powershell
.venv\Scripts\python.exe tools/collect_vehicle_scan.py list --max-pages 2
```

它先保存当前页，然后最多向左滑一次并保存下一页。若已手动进入**车辆详情页**，运行：

```powershell
.venv\Scripts\python.exe tools/collect_vehicle_scan.py detail --max-cars 2
```

它先保存当前车，然后最多点一次左箭头。默认上限均为 3，可逐步增大到 `--max-pages 100` 或 `--max-cars 400`。运行目录为 `debug/vehicle_scans/<时间>/`，包含原始 PNG、逐页 JSON、列表标注图和 `summary.json`；也可用 `--output-dir` 指定路径。单独任务达到上限会报告 `page_limit`/`car_limit`，串联任务会报告 `partial` 并在两个阶段分别记录具体原因，不称为完整扫描。任务不会自动恢复游戏停留位置，也不会切换“仅拥有”开关；要收录未拥有车辆，先手动关掉开关。

从选车列表一口气完成“小范围列表扫描→安全点击车身→详情遍历→按车辆 ID 合并”可运行：

```powershell
.venv\Scripts\python.exe tools/collect_vehicle_scan.py both --max-pages 1 --max-cars 2
```

串联模式只从最后一页选择**已识别且完整可见**的车卡，点击左侧车身，并核对详情页 ID 与所点卡片一致；不一致就停止，不开始向左遍历。运行目录的 `vehicles.json` 合并两种画面的字段：相同值保留来源，冲突值置为 `null` 并列在 `conflicts`，无法识别的卡片列在 `unidentified`。独立列表或详情模式也输出该汇总文件。

已在 MuMu 实测两页列表，以及从青铜首车自动进入详情、向左进入传奇末车的串联流程，再手动恢复到原青铜列表。完整段位及整车库遍历、弹窗中断与更多分辨率仍未实机验证。遇到不认识的页面时工具等待至多 12 秒后停止并保存截图。

要把**列表 OCR** 逐段位推广到高段位，可在多人选车列表运行限量采样：

```powershell
.venv\Scripts\python.exe tools/sample_vehicle_leagues.py --leagues 白金 翡翠 钻石 精英 宗师 传奇 --max-pages 2
```

工具先读取当前选中的段位和“仅拥有”状态；每个目标段位点一次段位图标，确认粉色下划线与列表出现后，按页数上限采样，并在退出时恢复原段位。它不会切换“仅拥有”、点击车卡、打开详情或开始比赛。报告写入 `debug/vehicle_scans/league_survey_<时间>/survey.json`，各段位保存原图、逐卡 JSON 和标注图，汇总车辆写入 `vehicles.json`。`page_limit` 表示本次达到采样上限，**不是**扫完整段位。

在“仅拥有”关闭时，白金至传奇各采最多十页，共定位 183 次完整车卡观测、129 辆不重复车型；183 次名称均匹配到目录。传奇在第九页触发重复画面的停止条件，其余段位达到人为页数上限，尚不能声称整段位已扫完。短名 `TECHRULES AT96` 单凭文字对应两辆车，只有选中的段位使其指向钻石的 Track Version；段位读不出或同段位仍有多个候选时继续报告未知。性能分 OCR 若在高段位明显丢失千位数则置为未知，不把 `972/4020` 当成有效分数。列表样本有遮挡、未拥有车和文字识别缺失，字段覆盖率低于名称识别率。

另对现有 48 张选车截图做批量 OCR，与高段位采样合并后，共有 353 次完整车卡观测、195 辆不重复车型，名称均匹配到目录。复制的完整参考 CSV 只作旁路校验：已识别样本中没有性能分高于参考最高值或图纸需求不在参考序列中的情况；One77、FFZERO1、Panamera 的目录段位与参考 CSV 不同，沿用用户已审核的段位。修订后的参考表已有 338 个唯一车名，包括 Tushek Aeon E；与已审核目录仍有 8 处段位差异。完整车型名单见 [已识别车辆](recognized_vehicles.md)，原图和逐卡异常在本机 `debug/vehicle_scans/survey_higher_tiers_10pages/`。

```powershell
.venv\Scripts\python.exe tools/crosscheck_vehicle_scan.py debug/vehicle_scans/survey_higher_tiers_10pages --additional-records debug/vehicle_scans/existing_selection_captures.json
```

## 接入实时扫描的顺序

1. **单页列表**：已经用卡片顶边及底边定位完整卡片；按卡片相对坐标读取文字、燃油、图纸、金/蓝底色；OCR 名称与目录匹配。同一车辆的不同字段后续可用详情页复核。识别失败时保存原图和字段区域，不能猜车名或点击图纸区域。
2. **自动翻页与标注**：独立采集器已能逐页截图、识别、按车辆 ID 去重，并保存原图、JSON 和带框预览。固定距离滑动后用页面指纹和图像差异判断是否有新车，连续重复或达到安全上限即停，不能仅靠固定滑动次数推断整段位已扫完。整段位结束条件仍需长距离实机验证。
3. **详情页遍历**：独立采集器只用左箭头切换，识别当前车名并按 ID 去重；遇到初始 ID 再次出现、连续车辆重复或异常页面即停。进入每辆车详情是读取信息，不点击图纸 `+` 或“开始”。车名滚动时重试一帧；长时遍历仍需用列表读到的 ID 复核。

列表页卡片颜色才给出“完全升级”，详情页提供准确的油量与性能等信息；两类记录按车辆 ID 合并，出现矛盾时保留两份证据并标记待复核。

## 自动采集控制器设计

采集必须作为独立任务运行，不接入会点击“开始”的多人循环。一个任务内共用截图、识别和报告模块，控制器分为列表扫描与详情遍历两个阶段。先只允许列表扫描和只读截图；确认卡片定位与停止条件后，再开放详情页箭头操作。

### 列表扫描

1. 当前独立采集器保持“仅拥有”开关和段位按钮原样，从当前列表位置开始。未来做整段位无人值守采集时，再记录开关状态、按任务需要切换并在结束后恢复，然后点击指定段位按钮建立已知起点。
2. 等待画面稳定，截取原图。定位两行车辆卡片外框，只处理完整可见的卡片；裁剪相对区域读取名称、级别、性能、油量、图纸和底色。每张卡片保存 OCR 原文、置信度、矩形、页号及截图路径。无法确定 ID 的卡片保存为 `unknown`，不靠位置猜名称。
3. 先写入本页数据，再使用现有列表向左滑手势（从 `(1000,420)` 到 `(600,420)`，320 ms）。滑动后至少等待当前画面不再变化，再截图。邻页可以重叠，无须精确移动一整卡宽；按车辆 ID 去重，字段变化则保留新观察及旧来源。
4. 每页生成由**从左到右、从上到下的完整卡片 ID 和位置**构成的指纹，辅以列表区域图像差异。连续滑动后图像几乎不动且指纹重复数次才判定到边；滑动经过一段新内容后重遇起点指纹属于异常重置，不能报告列表环绕完成。青铜是选车列表左边界；详情页左右箭头另有独立环绕。单次没有新车不能判定到边。另有总页数、总时长上限，触发时报告 `partial` 而非误报完成。
5. 未来的整库采集应每段位独立执行并记录选中的段位与实际识别到的车辆段位。列表可能跨段位；遇到下一段位时可停止当前段位，再从下一个段位按钮建立新起点。最终用车辆 ID 合并重复卡片。当前独立列表工具只从用户停留的位置扫描；限量段位采样工具可自动切段位并恢复原段位，但尚不判断整段位已扫完。

列表采集输出 `scan_id/pages/0001.png`、`0001.json` 和带卡片框的 `0001_annotated.png`。JSON 中保留每页所有候选，汇总文件按车辆 ID 存放最新可信值与证据路径，并列出 `unknown`、冲突和未扫描完的段位。标注图由采集结束后的本地绘图工具生成，避免给 Agent 发布包增加绘图依赖。

### 详情遍历

从列表中已确认 ID 且车身完整可见的卡片进入详情，点击点取卡片左侧车身，不碰图纸区。确认详情页左右箭头后，保存起始车辆 ID，读取当前页，之后只点**左箭头 `(495,360)`**并在每次切换后复核页面确实变化。现有倒序兜底使用同一按钮；用户已确认青铜首车向左会环绕到最后一辆，因此左行遍历有已知的环绕条件。具体按钮坐标须以 1280×720 画面复核。

每辆车保存详情原图、OCR 和结构化字段。车名滚动时采两三帧并同目录候选名比对；名称仍不确定就标为 `unknown`，不能把它当成环绕锚点。切车后连续多帧仍是同一辆车或页面消失时停止并报告异常。至少成功移动一次后，再次识别到**起始车辆 ID**才视为完整环绕；青铜首车向左会跳到最后一辆，因此绝不按段位边界判断遍历已结束。再设目录数量加余量的切换上限和总时长上限，避免误识别造成死循环。

详情只能更新其确实显示的字段；没有燃油角标就保留 `fuel=null`。列表金/蓝底色判断的 `fully_upgraded` 与详情结果按 ID 合并，但详情不得用“最高”、满星或性能分代替金卡判断。遇到广告、服务器错误或未知弹窗时先停采集并保存原图；不要让采集器自动点击“开始”或图纸 `+`。
