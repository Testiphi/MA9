# 全局车库只读实机诊断（05AK-C）

该入口尚未在任何真实设备上运行过；以下命令是待用户执行的首跑步骤，不是实机验收结论。

本文件说明如何由**用户在本人机器上手动执行**一次只读实机诊断：采集有限帧的原生
1280×720 画面，对每帧做 OCR 并调用离线 Observation 适配器，记录证据。本文档只写
步骤，本轮开发**不执行**任何 `live` 命令。

## 范围与边界（先读）

- **只读**：工具唯一的写操作是往证据目录里写文件。它不点击、不滑动、不按键、不
  触摸、不执行 shell、不加载 pipeline bundle、不派发任务；只加载你显式指定的 OCR 模型。
- **不驱动规划**：本工具不调用规划器 `global_garage_prepare_plan`，不产生 `ActionResult`，
  不写 `ready`，不修改账号。回车/人工点击**不是**系统动作回执；本阶段只核验画面观察
  与人工时序证据，自动规划事务与执行器是下一阶段。
- **观察语义分离**：`Observation` 仍是适配器的 `executable=false` / `offline_only` 语义；
  外层记录 `source=live_capture` 只表示像素来自本次实机采样来源，两者不合并成设备授权。
- **无自动发现**：ADB 可执行文件路径、设备地址、OCR 模型目录都必须显式给出；不扫描、
  不自动选设备、不读取旧账号配置、不执行 shell。
- **原生尺寸**：工具以 raw 尺寸截图，不缩放。图像不是 1280×720 的帧按失败记录，**不会**
  被静默归一化。请先把设备/模拟器配置成原生 1280×720 再运行。

## 前置条件

1. 设备/模拟器已配置为原生 **1280×720**。
2. 你已知 ADB 可执行文件路径与该设备地址。历史地址 `127.0.0.1:16384` 仅**供核对**；
   本工具不会自动连接它，也不会自动选择设备。
3. 仓库根目录有 OCR 模型目录（示例：`assets/resource/model/ocr`）——路径由你确认后填入。
4. 你已手动进入游戏里的**全局车库**页面（工具不负责主页面入口与导航）。

## 命令模板（PowerShell，路径由你填写）

```powershell
$py  = "E:/hzz/work/MA9/.venv/Scripts/python.exe"
$tool = "E:/hzz/work/MA9/MA9-worktrees/duel-scan/tools/diagnose_global_garage.py"

& $py -X utf8 -B $tool live `
  --adb-path "C:/path/to/adb.exe" `
  --address  "127.0.0.1:16384" `
  --ocr-model "E:/hzz/work/MA9/assets/resource/model/ocr" `
  --frames 40 `
  --interval-ms 1000
```

- `--frames`：`1..120`，默认 `40`。
- `--interval-ms`：`500..2000`，默认 `1000`。
- 计划采样时长 `frames × interval-ms` 必须 ≤ 120000 ms（例如 120×1000 合法，120×2000 非法）。
- `--output-root` **默认**是解析后的 MA9 根下的
  `MA9-evidence/20260929-05AK-C-live-observation/live`（根 checkout 与 lane 都解析到同一个
  最外层 MA9 根，因此默认同一个目录）。也可以在同根内显式指定其他证据目录。工具会 `resolve`
  后校验：不允许逃逸出 MA9 根，不允许 `..` 逃逸，不允许覆盖已存在的会话目录。
- 运行前会依次校验参数、解析并创建**新会话目录**（排他创建），然后才惰性导入 Maa/ADB 并连接。
  参数非法、目录逃逸或会话已存在都会在**连接之前**退出（退出码 2），不会初始化 SDK。

先看帮助（不连接任何设备、不初始化 SDK）：

```powershell
& $py -X utf8 -B $tool --help
& $py -X utf8 -B $tool live --help
```

## 建议的一次短操作序列

工具开始采样后，请按顺序做**一次**短序列（每步之间留出 ≥1 秒，让采样覆盖到稳定画面）：

1. 停在任意列表位置（不要求从 D 级起点开始）。
2. 打开筛选面板。
3. **改变「已拥有」勾选**，然后点「完成」提交。
4. 观察列表回到 **D 级最左端**（工具应把 `d_start` 观察为 `True`）。
5. 重新打开筛选面板核对。
6. **不改任何设置**，直接点「完成」关闭（应保持位置）。

可选补充（都不是程序动作回执）：

- 若初始「已拥有」是开，可以人工先 **off 提交**、再 **on 提交**。
- 另做一段短序列：**手动离开 D 起点**（例如滑到别的等级），确认后续帧里 `d_start`
  不再保持 `True`。

不需要重做已完成的五车分配，也不需要清空车辆。运行前无需解锁、升星或开赛。

## 输出结构

会话目录（新会话，绝不覆盖）：

```
<output-root>/<session-id>/
  manifest.json                 # 会话元数据（参数、预算、来源、等待/清理限制声明）
  summary.json                  # 最终 summary（状态/原因/预算耗尽标记/逐帧记录/退出码）
  maa/                          # Maa 运行期临时/日志目录（留本机，不提交）
  frames/
    0001.png                    # 每帧独立的原生 1280×720 BGR 像素副本
    0001.ocr.json               # 该帧的 OCR 结果（同帧绑定）
    0001.observation.json       # 该帧的 Observation + 诊断
    ...
```

- 默认逐行输出每帧：`frame=0001 page=... owned=... clear=... d_start=... png=frames/0001.png`。
  缺证据一律 `unknown`/`-`，不会猜。
- 像素完全相同是允许的：**两次成功采样就有两个 `frame_id`**；单凭相同像素不等于两次采样。
- 没有「用回放文件冒充 live」的选项。

## 状态、回传与退出码

| summary.status | 含义 | 退出码 |
| --- | --- | --- |
| `success` | 计划帧全部成功采样 | 0 |
| `partial` | 有成功帧，但也有失败帧/预算耗尽而提前结束 | 3 |
| `failed` | 没有任何成功帧，或连接/保存/OCR 等致命错误 | 1 |
| `cancelled` | 你按下 Ctrl+C 取消 | 130 |

参数错误由命令行解析器处理，退出码 2。若最终的 `manifest.json`/`summary.json` 无法写入，
工具在 stderr 打印 `ERROR: ...` 并返回退出码 4（不删除已存在的证据，也不声称写成了报告）。

回传时请给出：

- `summary.json`（含 `status`、`reason`、`budget_exhausted`、`frames_ok/frames_failed`、
  逐帧记录、`exit_code`）；
- `manifest.json`（参数与预算、来源、等待与清理限制声明）；
- 必要时对应的帧编号与 `frames/00NN.png`、`00NN.ocr.json`、`00NN.observation.json`。

## Ctrl+C、超时与清理的真实语义

- manifest或最终summary写入时按Ctrl+C，也会尝试写cancelled报告；取消报告最多尝试两次。持续中断或磁盘写入故障时，summary可能缺失/不完整，工具明确输出ERROR并以130（重复取消）或4（写失败）退出，已有证据不删除。

- 连接初始化各阶段也检查总预算；模型加载耗尽预算后不会再发起连接。
- 清理异常写入 `cleanup_errors` 并返回非零码，保留已有帧证据；释放采样闭包失败时仍尝试设备资源收尾，不把清理失败报成 success。

- **取消**：你可以随时按 **Ctrl+C** 停止——包括 SDK 导入、模型加载、连接、采样或收尾阶段。
  会话一旦建立，工具就会为这些阶段统一给出终态报告：能写成时写真实 `cancelled`/`failed`
  summary 并保留已写证据，退出码 130（取消）或非零（异常）。不会用 `os._exit` 掩盖退出错误。
- **总预算**：120 秒单调时钟，覆盖连接与采样。**绝对截止贯穿每个阶段**：一旦超过截止，
  就不再启动下一阶段的 capture/OCR/observe；已经产出的证据（PNG，其次 OCR）保留，
  该帧记为预算耗尽而不是成功；即使最后一帧完成，只要截止已过，`status` 也不会是 `success`，
  而是 `partial`/`failed` 且 `reason=time_budget_exhausted`。
- **连接与等待的真实限制**：本机 Maa python SDK 的等待接口没有超时/取消参数
  （`Job.wait()` 无超时地阻塞）。工具采用「按单调时钟轮询作业状态」的有界等待：到点就停止
  等待、放弃该句柄，并如实报告为超时；**它无法强制终止一个永不返回的底层调用**，也不会伪造
  超时 API。已 `done` 的作业即便已过截止也按已完成接受——截止只限制“等待多久”。
- **清理的真实限制**：收尾顺序是「先释放采样闭包，再 tasker → controller → resource」，
  并 `gc.collect()` 作为尽力而为的推进。SDK 在析构中释放原生句柄，这**不是** Python 侧可限时
  或可取消的操作；本工具不声称硬性限时的销毁，也不把 `gc.collect()` 当作原生硬超时的证明。

## 本阶段核验什么

- 每帧日志与 `Observation` 对 **page / 控件状态 / D 起点** 的实际观察；
- 人工短序列产生的时序证据（例如「改动并完成后回到 D 最左端」的顺序）；
- 观察与真实画面一致。**不以人造 `ActionResult` 达成 READY。**

没有支持的真实状态时，请如实记录为缺口（`unknown`），不要据此大量试错，也不要为了
让工具「通过」而解锁、升星或改变账号资格。
